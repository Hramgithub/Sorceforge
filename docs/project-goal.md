## 1. Цель в одном предложении

**Sourcefold превращает PDF настольной ролевой игры (сейчас — сценарии
Call of Cthulhu 7e) в документально точный двуязычный пакет данных — текст,
таблицы, раздатки, статблоки, арты и метаданные с привязкой к странице
исходника и общему словарю терминов, — из которого собирается единая база
для веб-помощника Хранителя и модуля Foundry.**

## 2. Экосистема и место Sourcefold

```text
PDF сценариев (EN, у владельца; реестр хешей)
        │
        ▼
┌──────────────────────── Sourcefold ────────────────────────┐
│ реконструкция → структура → сущности → перевод → проверка  │
│ выход: ПАКЕТ СЦЕНАРИЯ (JSON по общим схемам + арты)         │
└────────────────────────────────────────────────────────────┘
        │                      ▲ общий словарь терминов
        │                      │ (Hramgithub/CoC, terminology/)
        ▼
  СБОРКА БАЗЫ  ◄──── ПАКЕТ ПРАВИЛ (данные git_coc, переведённые в общий формат)
        │
        ├──► веб-помощник Хранителя (git_coc / keeperhelper.ru) + раздел «Сценарии»
        ├──► модуль Foundry (NRI FoundryVTT/modules/nri-coc-library, CoC7 8.13)
        └──► DOCX / читаемые книги — отдельный проект, не Sourcefold
```

## 3. Что входит в Sourcefold

1. **Реконструкция EN-источника** с привязкой к странице (`physical_page`,
   `bbox`) — ядро kb_creator (три вида MinerU + аудит покрытия).
2. **Структура книги**: разделы и блоки в порядке документа.
3. **Сущности**: персонаж/NPC/существо/преген, заклинание, том, оружие,
   раздатка, таблица, карта, арт, термин. Статблоки типизируются полностью,
   рядом всегда `raw` (D12a).
4. **Перевод**: сначала текст книги, затем поля сущностей по карточкам; общий
   словарь и книжный список терминов; валидатор согласованности (D12d).
5. **Проверки**: каждое `raw` есть в исходном фрагменте, числа сходятся, нет
   потерянных строк; флаги `needs_review`, `ocr_suspect`, `parse_uncertain`.
6. **Пакет сценария**: `manifest.json`, `structure.json`, `entities/`,
   `art/`, `terms.json` по общим JSON-схемам.

## 4. Что не входит

- DOCX, HTML, PDF и любые читаемые издания — отдельный проект (D12).
- Конвертация 5e/6e → 7e — отдельный конвейер (D12b).
- Слияние одинаковых сущностей между книгами — сборка базы; Sourcefold ставит
  только ссылку `same_as` (D12c).
- Веб-интерфейс и экспорт в Foundry — потребители базы, не Sourcefold.
- Исходные PDF в Git — нет; только реестр хешей (D7).

## 5. Критерии достижения цели

Цель считается достигнутой, когда для пилотного сценария (D12e):

1. **Одна команда** обрабатывает новый PDF до пакета без ручного написания
   JSON и без постраничных скриптов.
2. Пакет **проходит валидаторы схем** и проверки `raw`/чисел/покрытия.
3. Все статблоки, таблицы и раздатки пилота **извлечены как сущности**;
   неуверенные места помечены флагами, а не пропущены.
4. Русский текст и поля сущностей **согласованы по терминам** с общим
   словарём; расхождения объяснены.
5. **Владелец принимает** пакет одним решением после выборочной проверки.
6. **Сборка базы** из пакета пилота и пакета правил даёт данные, которые
   открываются в веб-помощнике (раздел «Сценарии») и импортируются в
   `nri-coc-library`.

## 6. Уроки, которые закладываются в архитектуру

Из аудита Sourcefold Phase 0 и анализа kb_creator:

- **Процесс не важнее продукта.** Одно человеческое «принято» на пакет или
  главу, git-коммиты как доказательство; без многоступенчатых разрешений на
  каждый шаг.
- **Нет кругового контроля.** Эталон для оценки OCR не пишется тем же агентом
  из той же картинки; подстановка эталона не выдаётся за проверку.
- **Нет постраничных скриптов.** Логика конкретной книги — только в данных
  пакета или в конфигурации, не в коде.
- **Схемы — источник правды**; идентичность прогона = входы + версия пакета +
  версии схем (изменение кода не обесценивает прогон).
- **Подключаемые инструменты и агенты** (адаптеры), переносимые прогоны,
  Python 3.12 + `uv.lock` (D6), инструменты по манифесту с хешами (D4).
